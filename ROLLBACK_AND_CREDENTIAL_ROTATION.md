## 1. Executive Summary & Purpose

This operational runbook provides exact, step-by-step procedures for:
1. **Manual MongoDB Atlas Credential Rotation:** Neutralizing legacy database credentials present in historical commits without downtime or operational interruption.
2. **Cryptographic Secret Generation:** Securely generating 256-bit secrets for `JWT_SECRET` and provisioning initial admin passwords.
3. **Application Rollback Plan:** Safely reverting code deployments while preserving database consistency.

## 2. Safe Manual MongoDB Atlas Credential Rotation Procedure

> [!WARNING]
> Historical git commits previously contained connection strings. To ensure zero-trust security before staging/production launch, rotate the database user credentials in MongoDB Atlas following this zero-downtime procedure.

### Step 2.1: Create New Staging / Production Database User
1. Log in to the [MongoDB Atlas Console](https://cloud.mongodb.com/).
2. Navigate to **Security** > **Database Access** > Click **Add New Database User**.
3. Choose **Password** authentication:
   - **Username:** e.g., `gatecode_app_prod` (or `gatecode_app_staging`)
   - **Password:** Click **Autogenerate Secure Password** (minimum 24 characters) and copy it to a secure password manager.
4. Set **Database User Privileges**:
   - Select **Built-in Role**: `Read and write to any database` OR restrict to specific database: `readWrite@gatecode_cars24`.
5. Click **Add User**.

### Step 2.2: Retrieve Clean Connection URI
1. Navigate to **Deployment** > **Database** > Click **Connect** on your cluster.
2. Select **Drivers** > Node.js (version 5.5 or later).
3. Copy the clean connection string:
   ```text
   mongodb+srv://gatecode_app_prod:<password>@<cluster-host>.mongodb.net/gatecode_cars24?retryWrites=true&w=majority&appName=GatecodeCars24
   ```
4. Replace `<password>` with the autogenerated password from Step 2.1.
5. **Never commit this URI to Git.**

### Step 2.3: Update Deployment Environment Variables
1. In your hosting provider (Vercel / AWS / Docker / Kubernetes / Render):
   - Update `MONGO_URI` with the new URI.
2. Trigger a rolling redeploy or update environment configuration.
3. Verify application health check (`/api/health` or visiting login screen).

### Step 2.4: Revoke Legacy Database User
1. Once all active application instances are confirmed connected with the new user, return to **Database Access**.
2. Locate the old database user (e.g., legacy user from historical commits).
3. Click **Actions** (`...`) > **Delete User**.
4. Confirm deletion. The legacy connection strings in git history are now completely invalid and inert.

## 3. Cryptographic Secret Generation (JWT & Admin Password)

### 3.1: Generate Production `JWT_SECRET`
Generate a high-entropy 256-bit hexadecimal secret:
```bash
# On Linux / macOS / Git Bash:
openssl rand -hex 32

# On Windows PowerShell:
-join ((65..90) + (97..122) + (48..57) | Get-Random -Count 48 | ForEach-Object {[char]$_})
```
Set this value as `JWT_SECRET` in the staging/production environment variables.

### 3.2: Configure `ADMIN_PASSWORD`
Provisioning an administrator account requires `ADMIN_PASSWORD`.
- Choose a strong administrative password (minimum 16 alphanumeric + special characters).
- Set `ADMIN_PASSWORD` in the deployment environment.
- On first boot, the application seeds the admin with a 10-round bcrypt hash.
- Rerunning or rebooting the application will **never** overwrite or reset this password.

## 4. Application Rollback Plan

### 4.1: Code Rollback
If an unexpected issue arises in staging or production:
1. Revert to the previous stable release commit or branch:
   ```bash
   git checkout <previous-stable-tag>
   # or in hosting provider, click "Rollback to previous deployment"
   ```
2. Redeploy the prior build.

### 4.2: Database Backward-Compatibility
- All schema updates made during remediation (such as compound indexes and `suppressReservedKeysWarning`) are strictly backward-compatible.
- No collections, fields, or documents have been dropped.
- Older application versions can read and write to the database without schema conflict.

### 4.3: Rollback Verification
Following a rollback, confirm:
1. Application serves 200 OK on login `/`.
2. Users can authenticate with active credentials.
3. Orders, Returns, and Customer leads load successfully.
